# 从代码到机器动作

> **阅读索引**：工程故事路线第 2 篇。前置：[先把需求说成明确条件](../00-Mathematical-Foundations/requirements-as-logic.md)。下一篇：[让程序结构可理解](../03-Programming-Languages/why-programming-languages-need-structure.md)。

## 故事：同样的计算，运行时间不同

订单金额计算在小规模数据上很快，批量导入数万条记录后却明显变慢。团队先怀疑“语言慢”，但原因也可能是内存访问、缓存命中、分支、分配或输入输出。

## 为什么要理解它

高级语言隐藏硬件细节，让我们专注业务；但程序最终仍要在处理器上执行，并从存储层次取用数据。理解基本结构有助于提出可验证的性能假设，而不是凭语言名称下结论。

## 核心原理

处理器依据指令集架构（Instruction Set Architecture, ISA）执行机器指令。寄存器是靠近处理器的快速工作空间；主存容量更大，访问通常更慢。缓存利用程序会重复访问相同或相邻数据的规律，减少平均访问延迟。

源代码一般要经过编译或解释以及运行时处理，变成底层操作。具体过程取决于处理器、编译器、运行时和工作负载，一行高级代码不等于一条机器指令。

## 工程上解决什么

若对象分散在内存中，处理器可能频繁等待数据；连续访问热点数据更可能复用已读内容。优化时先测量，再针对瓶颈改变访问模式，并在相同输入和环境下比较结果。

## 常见误区

- 一行代码不必然对应一条指令。
- 处理器频率高不代表所有程序都快；内存等待和并行度同样重要。
- 缓存容量有限，访问模式不佳时仍会频繁未命中。

## 工程哲学：用测量替代硬件直觉

硬件知识帮助提出假设，基准测试和性能分析决定假设是否成立。记录输入规模、环境和测量方法，避免把噪声误认为优化。
