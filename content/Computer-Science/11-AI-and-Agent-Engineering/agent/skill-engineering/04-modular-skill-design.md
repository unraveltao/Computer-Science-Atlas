# 怎样组织复杂技能的规则与资源

> **本篇问题**：一个技术研究 Skill 的规则从二十行增长到几百行。我们应该继续往 `SKILL.md` 里追加，还是拆成更多文件？

## 本篇索引

通过“研究一个技术工具是否适合项目”的案例，学习：

- `SKILL.md`、`references/`、`scripts/`、`assets/` 各自承担的职责；
- 渐进式加载（Progressive Disclosure）为什么能减少不必要的上下文；
- 何时拆分内容、何时维持简单结构；
- 如何检验文件组织确实改善了可维护性，而不是制造新的寻找成本。

前篇讨论了[怎样让技能遵守用户目标](./03-skill-behavior-design.md)。本篇关注的是**规则越来越多之后怎样继续保持可靠**。

## 一、问题出现：每次研究都读完一本说明书

假设我们写了一个 `technology-research` Skill，专门帮助开发者判断某个工具是否值得使用。

第一版只有三条要求：查官方文档、比较优缺点、给出结论。很快，真实使用暴露出更多情况：

- 研究开源库时，需要核对许可证和维护状态；
- 研究 API 时，需要核对版本、认证方式和调用限制；
- 研究桌面软件时，需要检查系统兼容性与安装渠道；
- 对所有研究，都需要区分来源、推测与实际验证。

如果把这四类内容都直接堆在 `SKILL.md` 中，不管任务简单复杂都重复阅读，入口就会越来越难维护。此时的真正问题不是“文件太长”本身，而是：**哪些规则始终需要，哪些规则只在特定任务中需要？**

## 二、用职责而不是文件数量来划分

根据 [Agent Skills 规范](https://agentskills.io/specification)，Skill 至少需要 `SKILL.md`，其他资源是可选的。

| 位置          | 应放什么                               | 本例                                       |
| ------------- | -------------------------------------- | ------------------------------------------ |
| `SKILL.md`    | 适用范围、通用步骤、选择分支和关键边界 | 明确研究问题，优先官方资料，按场景加载参考 |
| `references/` | 信息量大、只在某些情况需要的说明       | 开源许可证核对清单、API 兼容性清单         |
| `scripts/`    | 可重复且适合程序化的操作               | 对本地保存的候选表做字段校验               |
| `assets/`     | 生成结果会使用的固定素材               | 报告的空白模板、图标资源                   |

注意 `references` 不一定是“独立知识库”，而是该 Skill 执行任务时可按需读取的细节。它们不应该与入口规则相互矛盾。

## 三、最小的模块化版本

```text
technology-research/
├── SKILL.md
├── references/
│   ├── open-source.md
│   └── api.md
└── assets/
    └── comparison-template.md
```

这里暂时**没有** `scripts/`。如果当前任务只要阅读文档和作比较，脚本并不是必须的。等后续出现真实、重复的机器处理需求，再引入脚本。

入口文件可以写成：

```markdown
---
name: technology-research
description: 当用户需要研究和比较软件工具、开源库或 API 是否适用于某个项目时，收集可核查的来源，比较适用范围、限制与风险，并给出有依据的结论。
---

# 技术研究

1. 确定用户要做的事、约束和评价标准。
2. 优先核对官方文档与原始来源；无法联网时说明限制。
3. 如果研究开源项目，请按需读取 references/open-source.md。
4. 如果研究 API，请按需读取 references/api.md。
5. 结果区分：已核实事实、推断、尚待验证事项。
6. 不根据不完整摘要声称“读过完整源码”。
7. 没有授权时不安装未知程序，不运行远程脚本。
```

这不是要求 Agent 每次都加载两个参考文件，而是明确**触发条件**。当问题仅是“比较两个 API 的认证方式”时，开源许可证清单未必有用。

### 参考文件该怎么写？

`references/api.md` 可以包含：

```markdown
# API 核对清单

只有当任务涉及 API 的能力、集成或选型时读取。

- 官方版本与弃用状态
- 认证方式与权限模型
- 速率限制、成本与数据保留政策
- 最小调用示例是否来自官方
- 失败行为与重试约束
- 用户环境适配情况
- 仍缺少的验证信息
```

这一组细节不会遮蔽入口的主要职责，却能在真正需要时提供更完整的检查依据。

## 四、渐进式加载不等于自动魔法

渐进式加载（Progressive Disclosure）的思想是：**先加载选择所需的少量信息，在确定任务相关后，再读取更详细的指令和资源**。

很多支持 Skill 的环境可能先利用 `name`、`description` 进行选择，再加载正文；但每个客户端的读取机制不一定相同。因此，不能写一条“按需读取”就断言运行时一定减少了 Token 消耗。

需要区分：

1. **设计意图**：只要求读取当前任务相关的参考文件。
2. **实际行为**：Agent 是否真的只读取了需要的文件。
3. **运行效果**：是否避免遗漏关键规则、提高了任务质量。

后一项需要在能提供轨迹或可靠观测的环境中测试。

## 五、动手实验：比较单文件和模块化版本

准备两个功能要求等价的教学版本：

- **版本 A**：将通用规则、开源核对清单与 API 核对清单都写在一个 `SKILL.md`。
- **版本 B**：使用本篇的文件结构，入口只保留通用流程与条件性引用。

对两个版本分别测试：

| 请求                           | 应该用到的规则 | 需要观察的行为                                       |
| ------------------------------ | -------------- | ---------------------------------------------------- |
| “这个开源库能用于商业产品吗？” | 开源许可证核对 | 是否根据准确许可证文本分析，是否知道不能代替法律意见 |
| “这两个 API 哪个支持 OAuth？”  | API 核对       | 是否核对版本与官方文档                               |
| “给我一份简短的工具选型建议。” | 通用流程       | 是否不过度展开不相关清单                             |
| “离线情况下给我确定结论。”     | 来源可信度规则 | 是否标明无法联网核实，而非编造最新信息               |

记录：版本、客户端、模型、输入、读取的文件、实际结果、错误和证据。不能只用“B 比 A 短”证明 B 更好；还要判断它是否漏读了必要参考，是否增加了维护复杂度。

## 六、工程思想：高内聚、低耦合与按需依赖

**高内聚（High Cohesion）**指同一文件围绕明确职责组织内容：API 参考文件只讨论 API 评估，不夹杂大量会议纪要规则。

**低耦合（Low Coupling）**意味着入口知道何时读取参考资料，但不要求所有场景依赖每一份参考文件。

**按需依赖**意味着在确有需求前不急着引入脚本、服务或数据库。

不过，文件拆得越多也可能带来引用失效、上下文碎片化和维护成本。最佳粒度取决于真实需求，不存在所有 Skill 都必须拥有固定四层目录的规定。

## 七、总结与知识关联

本篇不是教“按模板创建 `references`”，而是解释**怎样从实际任务差异中找出可分离的职责**。入口用于任务选择和通用约束，条件性细节与素材放到合适的位置，文件数量随问题复杂度增长。

下一篇将面对更实在的问题：当 Skill 不再只给建议，而是要处理真实文件时，**哪些操作适合交给脚本，哪些判断仍应由 Agent 负责？**
