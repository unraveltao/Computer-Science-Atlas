# 怎样让技能遵守用户真正的目标

> **本篇问题**：Skill 明明被正确调用了，却干了用户根本没有要求的事情。为什么？

## 本篇索引

这次我们换一个案例：一位使用者希望设计一种“工具使用指导 Skill”，但 Agent 听见“工具使用”就直接开始教授某个工具。

你将学习：**任务意图识别 → 行为分流 → 输入输出契约 → 处理信息缺失 → 停止条件**。完成后应能给对话型 Skill 写出可测试的行为规则，而不只是含糊地要求“主动帮助”。

相关知识：[为什么技能没有被正确触发](./02-skill-discovery-and-triggering.md)。

## 一、触发成功，为什么仍会失败？

用户说：

> 我想设计一个能帮我学习陌生软件的 Skill，还不确定应该有哪些功能。

错误回应：

> 好的，第一课我们来学习 GitHub 的基础操作……

这里 Skill 可能真的被正确调用了，但它把**设计工具的需求**误判成了**现在使用工具的需求**。

真正的问题不在触发，而在技能内部如何理解本次任务。把用户的句子拆开：

- **对象**：“工具使用指导 Skill”是用户想开发的产品。
- **动词**：“想设计”，表示当前阶段要讨论需求与方案。
- **未确定信息**：“还不确定功能”，表示需要探索需求，而不是直接进入课程。
- **允许的输出**：需求草案、目标人群、主要场景、待决问题。
- **暂不允许的行为**：未经请求的安装、代码实现、启动一整套课程。

因此，用户提到某个工具名称，并不必然代表希望立刻学习或操作它。

## 二、为 Skill 定义行为契约

工程上的契约（Contract）回答：给定什么输入，允许产生什么输出，什么时候必须停止。

这里可以先把三类用户意图明确区分：

| 意图 | 典型请求                              | 允许的主要输出                     |
| ---- | ------------------------------------- | ---------------------------------- |
| 设计 | “我想做一个帮助使用工具的 Skill”      | 目标、需求、设计方向与关键不确定性 |
| 执行 | “用已经存在的 Skill 帮我研究这个工具” | 在已授权能力内执行任务、报告证据   |
| 探索 | “我不知道这种 Skill 值不值得做”       | 现有方案、需求差距、最小验证建议   |

用户意图可能是混合的。对于“先帮我设计，再给一个试用样例”，可以先设计，再在材料明确允许的范围内做样例；没有必要一开始把它强行固定为单一模式。

**重要的是不把关键词当成命令。** 关键词“GitHub”“课程”“Skill”都只是上下文的一部分，真正决定行动的是用户想让你做什么。

## 三、一个可执行的对话型 Skill 草案

```markdown
---
name: requirement-clarifier
description: 当用户想构思、评估或梳理一个软件、自动化流程或 Agent Skill 的需求时，帮助明确目标、使用场景、约束和最小验证；不自动切换为工具教学或代码实现。
---

# 需求梳理

先判断用户当前希望“设计”“探索”还是“执行”。
依据动词、上下文和明确授权判断，不仅依赖关键词。

设计意图：概括目标、核心用户、已有能力、约束和待验证假设；
信息足够时给出可评审的最小方案，不要无限追问。

探索意图：比较可行的工具或做法，区分已证实与待查证；
不要仅因为提到某个技术名词就转入教程。

执行意图：仅在具备权限、工具和明确请求时行动。
无法执行时说明阻碍，不要宣称已经操作成功。

只有当缺失信息会改变主要方案、权限或风险时，
才提出当前最关键的一个问题；能合理继续时先继续。

用户明确说“先不做”“结束”时停止推进，
不自行创建文件、代码或长期任务。
```

这份示例不是所谓“万能需求分析器”。它的职责是**帮助用户把尚未确定的目标梳理清楚**；真正实现、教学、调研都应在明确的请求或授权下进行。

此外，对话型 Skill 的规则不能取代工具权限检查。例如“执行意图”成立，并不自动意味着可以读取私人文件或向远端仓库推送。

## 四、动手练习：把含糊约束变成可观察行为

下列三句写法看起来友好，但难以测试：

- “根据情况适当追问。”
- “尽可能主动帮助用户。”
- “及时停止，不要啰嗦。”

为什么它们难验证？因为没有给出**判断条件**和**可观察输出**。

可以把它们改成：

1. 当缺失信息会实质改变方案或风险时，询问**一个**最关键的问题；否则先给可用的下一步。
2. 不把“设计意图”直接转成“工具教学”或“编写代码”；对于未被请求的动作先不要执行。
3. 用户明确表达暂停时停止该流程；不得把“暂停”理解为自动后台执行。

这不意味着规则越多越可靠，而是应该将最容易偏离的行为写得**足够具体**。

## 五、预测与验证：六个情境

下面是建议在目标客户端中运行的测试，不是已经完成的执行结果。

| 编号 | 用户输入                           | 预期主要行为                             |
| ---- | ---------------------------------- | ---------------------------------------- |
| A1   | “我想设计一个学习工具的 Skill。”   | 澄清产品目标；不直接教某款软件           |
| A2   | “先帮我判断是否有现成工具可复用。” | 给调研方向或查证结果，说明证据来源       |
| A3   | “就按刚才确认的方案写任务书。”     | 根据已确认信息产出任务书，不重问已知约束 |
| A4   | “暂时不要写代码，我们先讨论。”     | 仅讨论，不擅自执行                       |
| A5   | “结束这个话题。”                   | 结束，不自动追加新阶段                   |
| A6   | “帮我实际安装它。”                 | 检查授权与工具能力；不能把建议当作已执行 |

每条至少记录三项：**识别出的意图、实际输出或动作、与预期的偏差**。如果用户一句话同时包含两种意图，记录 Skill 如何决定先后顺序，不能仅用“选 A 还是 B”打分。

### 故障注入：两个容易出错的改写

- 将 A1 改为“我想设计一个教 GitHub 的 Skill”。Agent 是否因为出现 GitHub 就直接讲 GitHub？
- 将 A3 改为“先按方案写任务书，但不要执行它”。Agent 是否区分**生成任务书**与**真实执行**？

这些改写专门检验技能能否读懂用户的行动边界。它们比只用一条标准请求更有价值。

## 六、工程思想：封装的真正含义

把 Skill 视为一个具有**稳定职责**的工程模块，有助于理解封装（Encapsulation）：

- **模块对外的承诺**：帮助用户澄清目标与需求。
- **模块内部的方法**：识别意图、组织信息、必要时提问、提供草案。
- **模块不应该替用户决定的事情**：未经确认选择产品方向、发布代码或修改私有资料。

与函数封装类似，技能设计也需要明确“我负责什么”和“什么不是我的职责”。不同的是，技能通过自然语言约束模型行为，因此还需要测试语义边界，而不是仅靠类型检查。

还可以联系到单一职责原则（Single Responsibility Principle）：不是每一条用户请求都要交给同一个“万能 Skill”，尤其不要把**需求顾问、教师、执行者**强行合并在一个入口里。

## 七、本篇总结

一个 Skill 即使被正确触发，也可能完全做错事。解决方法不是增加更多热情的指令，而是从真实失败中提取**明确的输入输出契约、意图分流规则和停止条件**。

本篇完成的标准，是在真实客户端中验证多种意图下的行为边界，并保存输出证据；这里只提供了可复制的规则与测试方案。
