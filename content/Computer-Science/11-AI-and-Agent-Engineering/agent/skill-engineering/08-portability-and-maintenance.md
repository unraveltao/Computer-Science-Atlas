# 为什么换一个环境技能就失效

> **本篇问题**：同一份 Skill 在某台 Windows 电脑上的 Codex 可以使用，换一个客户端或项目后却找不到，或者脚本无法运行。是 Skill 写错了吗？

## 本篇索引

本篇使用一个**跨项目代码解释 Skill**，把“我这里可以用”拆成四类条件：**格式兼容、发现方式、运行依赖、权限与工具能力**。

读完后，你应当能为 Skill 写出明确的运行前提、版本信息和兼容测试清单，并知道不能把同一目录结构的存在等同于跨平台可用。

前置阅读：[怎样用测试证明技能真的可用](./07-testing-and-evaluation.md)。

## 一、一次迁移暴露四个不同问题

假设我们做了一个帮助解释代码的小 Skill：

> 选中一段源码后，分析它的输入、执行流程、关键状态和可验证的运行结果。

在当前机器上它使用得很好。后来另一个人复制了整个文件夹，却遇到：

1. Agent 看不到这个 Skill。
2. 能看到，但显式调用方式与原环境不同。
3. 技能调用了 `python`，但目标机器没有 Python。
4. 技能希望读取当前仓库，却没有文件访问能力。

这四种情况不能统称为“Skill 不兼容”；需要分层定位。

## 二、格式兼容和运行兼容不是一回事

开放规范主要定义 `SKILL.md` 的文件格式、必需元数据和可选资源组织。但具体的加载路径、技能选择与工具权限由**宿主客户端（Host）**负责。

| 层次 | 可以从什么确认 | 不能从什么推断 |
| --- | --- | --- |
| 文件格式 | `name`、`description`、目录名和正文满足规范 | 不能据此证明客户端会安装 |
| 发现方式 | 按目标客户端的官方指南放置并出现于列表 | 不能据此保证自动触发 |
| 行为能力 | 目标环境提供所需文件、工具与权限 | 不能从 `SKILL.md` 的文字推断有权限 |
| 系统依赖 | 可检查 Python、Node.js、Shell 等实际版本 | 不能假设每台机器都一致 |

例如文档说“执行脚本”并不能让系统凭空具备 Python。没有脚本运行能力时，Skill 可以改用只读解释模式，或者明确报告当前无法完成操作；不能伪称脚本已经执行。

## 三、先写出清晰的兼容边界

一个 Skill 的 `SKILL.md` 可以把通用能力和特殊条件分开：

```markdown
---
name: code-explainer
description: 当用户需要理解一段源码的输入输出、执行顺序、关键状态或主要设计意图时，结合可访问的代码进行解释；只有明确授权和工具能力时才执行验证命令。
---

# 代码理解

1. 明确用户给出的是哪段代码、来自哪里、想理解什么。
2. 没有代码时请求必要的内容，不捏造文件存在。
3. 先解释可从静态阅读确认的行为与不确定之处。
4. 当用户要求运行验证时，检查运行环境与权限。
5. 运行后记录命令、退出状态和实际输出。
6. 不把静态推断误写为已经运行的事实。
```

由于上述版本不依赖任何脚本，它更容易跨环境迁移。但这只能降低依赖，**不能保证不同 Agent 对相同代码的解释质量一致**。

如果后续增加脚本，则需要把对应运行环境和版本写清楚，并在缺失时提供明确的失败行为。

## 四、制定一份“环境契约”

建议每个需要工具执行的 Skill 至少记录以下内容：

- 目标客户端与已测试版本；
- 安装位置与发现方式的官方说明链接；
- 所需工具、命令、运行环境及最低版本；
- 访问文件、网络与写操作需要的权限；
- 不具备依赖时的降级行为或报错；
- 实际执行过的测试与尚未测试的组合。

例如：

```text
Skill: code-explainer
Host A: 已测试（具体版本、日期待填写）
Host B: 未测试
Python: 非必需；运行代码示例时按语言需要另行检查
Network: 默认不必需
Write access: 默认不需要
Observation: 静态阅读与实际运行须分别标明
```

这些字段的目的不是让 README 变长，而是避免使用者发现失败时无从判断是功能问题还是环境问题。

## 五、跨环境验证矩阵

先把目标环境分成你实际会使用的几组，不要一开始宣称支持所有 Agent：

| 测试场景 | 文件发现 | 显式调用 | 隐式选择 | 文件访问 | 结果 |
| --- | --- | --- | --- | --- | --- |
| 当前开发机 / 当前 Codex 版本 | 待测试 | 待测试 | 待测试 | 待测试 | 未验证 |
| 另一工作目录 / 相同客户端 | 待测试 | 待测试 | 待测试 | 待测试 | 未验证 |
| 另一台机器 / 相同客户端 | 待测试 | 待测试 | 待测试 | 待测试 | 未验证 |
| 其他支持 Skill 的客户端 | 待核对 | 待核对 | 待核对 | 待核对 | 未验证 |

建议先做两个最小实验：

**实验 A：只改变工作目录。** 不修改 `SKILL.md`，检查项目级与用户级技能的发现范围是否不同。

**实验 B：只改变客户端。** 同一 Skill 保持不变，核对目标客户端的安装说明和调用机制，再测试显式调用与输出。

每次只改变少量条件，更容易判断失败原因。如果两次同时换电脑、换系统、换模型和换 Skill 版本，观察结果就很难解释。

## 六、维护和升级的风险

Skill 会随着客户端版本、第三方 API、脚本依赖与用户需求的变化而过时。

应该给维护过程规定基本动作：

1. 记录当前已验证版本。
2. 修改前保存现有失败案例与测试集。
3. 对 `description`、规则或脚本作最小变更。
4. 重新跑触发正反例与关键行为测试。
5. 更新兼容说明，标明尚未覆盖的环境。

**文件格式兼容不等于语义兼容。** 例如把一个 Skill 的描述从“阅读代码”改成“处理所有软件工程任务”，可能影响其他技能的选择行为，即使 YAML 完全合法。

同样，版本号也不是质量证明；需要对应测试证据。

## 七、工程思想：依赖管理与向后兼容

**依赖管理（Dependency Management）**：明确技能真正依赖哪些工具，不要偷偷假设环境中一定存在某个命令。

**可移植性（Portability）**：将通用语义规则与宿主特定行为区分开，尽可能减少无意义的环境耦合。

**向后兼容（Backward Compatibility）**：修改技能后，过去合法的核心任务不应意外失效；这需要回归测试，而不是只声明兼容。

**渐进增强（Progressive Enhancement）**：没有工具时先提供确实能完成的静态解释；当有授权和运行能力时再补充动态验证。降级必须诚实，不能把“没有运行”描述为“运行成功”。

## 八、总结与知识关联

技能在一台机器上可用，仅证明它在**特定环境、输入和权限条件**下的表现。真正的可交付性要求把这些条件写清楚，并在目标环境中再次核验。

最后一篇，我们将不再靠照抄一份完整示例来“毕业”，而是从真实需求出发，独立走完需求、设计、实施、测试、风险审查和发布的过程。
