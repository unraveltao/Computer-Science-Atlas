# 为什么需要智能体技能

> **本篇问题**：为什么我们已经会让 AI 整理会议记录，还需要额外做一个 Skill？

## 本篇索引

完成阅读和练习后，你应该能够：

1. 从一次具体请求中分离**稳定的任务方法**与**每次变化的输入**。
2. 解释技能（Agent Skill）在智能体工作中的位置，以及它不能保证什么。
3. 看懂最小 `SKILL.md` 的元数据和指令，并在受支持的客户端中尝试调用。
4. 设计一组能区分“文件有效”“成功触发”“结果正确”的基本检查。
5. 把这次设计联系到软件工程中的**抽象（Abstraction）**与**复用（Reuse）**。

先有问题和输出目标，再判断要不要做 Skill；不是看到重复出现的词，就立刻新建一个文件夹。

## 一、事情从重复的会议纪要开始

假设团队每周讨论产品进度。每次会后，你都要向 Agent 解释：

- 请区分“有人提出的建议”和“大家已经确认的决定”。
- 提取真正的待办事项；缺少负责人或截止时间时明确标注，不要猜测。
- 如果我只要待办，不要额外生成一整篇摘要。
- 不得凭空补充会议上没说过的结论。

这些要求连续出现多次。不同的是会议材料与这次的输出范围；相同的是判断原则。

如果把每次请求都完整粘贴一遍，就会带来两个问题：一是容易遗漏规则，二是难以统一修订规则。于是产生一个工程问题：

> 能不能把稳定的“处理方法”保存起来，而把每次不同的“材料和目标”继续留在用户请求中？

这才是本例引入 Skill 的动机。

## 二、Skill 究竟是什么？

智能体技能（Agent Skill）可以理解为**供支持该机制的 Agent 按需读取的一组任务指导和资源**。按照 [Agent Skills 开放规范](https://agentskills.io/specification)，一个技能目录至少包含 `SKILL.md`，它使用 YAML 元数据描述技能名称和用途，正文说明如何处理任务；`scripts/`、`references/` 和 `assets/` 都是可选的。

最小结构：

```text
meeting-notes/
└── SKILL.md
```

不要混淆以下四件事：

| 概念 | 解决什么问题 | 本例 |
| --- | --- | --- |
| 用户本次请求 | 这一次到底要做什么 | “只提取这份会议记录的待办” |
| Skill | 对这一类任务有哪些稳定方法 | 区分决策和建议、标注缺失字段 |
| Agent | 如何理解目标、选择能力、协调执行 | 决定是否使用 meeting-notes，读取材料，形成结果 |
| 工具与权限 | 实际能够读写哪些内容 | 读取用户提供的会议文本、保存输出文件 |

**Skill 不是另一个独立的 Agent，也不是某种执行成功的保证。** 它只能为 Agent 提供可复用的方法与可选资源。运行结果还受模型、上下文、工具、权限和输入质量影响。

## 三、从需求中提炼稳定规则

先不要急着写 `SKILL.md`。用一张表把需求拆开：

| 每次变化的内容 | 可复用的规则 |
| --- | --- |
| 会议主题、日期、参加者 | 不把建议误写成已确认决策 |
| 用户想要摘要还是仅要待办 | 优先遵守用户指定的输出范围 |
| 本次会议材料 | 只使用材料明确支持的事实 |
| 负责人和期限是否出现 | 缺失字段标“待确认”，不要自行推断 |

这就是**抽象**：保留一类任务的共性，忽略与这项共性无关的具体差异。

抽象的边界也很重要。如果你的会议纪要 Skill 开始负责日程预订、员工绩效评分和合同审批，它就不再是一个清晰的单一用途工具。一个 Skill 可以扩展，但每次扩展都要回答“是否仍属于同一类用户意图”。

## 四、做出第一个最小 Skill

新建目录 `meeting-notes/`，在里面创建以下 `SKILL.md`。

```markdown
---
name: meeting-notes
description: 整理用户提供的会议记录或逐字稿，提取摘要、已确认决策及待办事项；适用于会后信息整理，也支持只提取某一类内容。
---

# 会议记录整理

根据本次用户请求及其提供的材料，整理摘要、决策或待办。
如果用户指定“只要待办”等范围，严格遵守，不额外扩写。

将提议、讨论中方案和已确认决策区分开。
只有材料明确表明达成一致，才可写为“已确认决策”。
不明确时写“需要确认”，不要推断。

待办尽量包含任务、负责人、截止日期。
材料未给出负责人或日期时，记录“待确认”，不要补造。

用户只笼统说“整理”时，可先提供有材料支持的摘要、
已确认决策与待办，并说明选择的整理范围。

如果未提供任何会议内容，不要编造会议事实；
若用户明确要求虚构演练，先明确标注所有材料均为虚构。
```

注意：

- `name` 是技能的机器可读名称；目录名与 `name` 需要符合规范。
- `description` 不只是介绍功能，还帮助支持该机制的客户端判断适用场景。
- 正文是任务处理约束，不是一次具体会议的记录。
- 一开始只用一个文件，是因为当前行为还简单。**不需要先凑齐四层目录**。

关于必需字段、命名约束与可选资源，以[官方规范](https://agentskills.io/specification)为准。

## 五、动手试用：把文件存在与功能有效分开

以下是**待你在真实客户端执行的练习**，不是已经通过的测试记录。

1. 阅读目标环境的安装说明。例如在 Codex / ChatGPT 中核对它支持的用户级或项目级 Skills 路径；不要照搬其他客户端的目录。
2. 把 `meeting-notes` 整个文件夹放到目标环境支持的位置。
3. 确认该环境确实列出了技能，必要时刷新或重新进入会话。
4. **先显式调用**该 Skill，使用下面的固定材料观察输出。
5. 再测试自然语言调用；注意，隐式触发可能受模型和上下文影响，不能保证每次成功。

固定演练材料（虚构）：

> 小组讨论网站发布。甲说：“建议周五上线。”乙说：“测试还没有结束，先别定。”大家确认：周四以前完成搜索页面检查。丙负责检查，但会议没有确认具体完成时间。

**请求 A**：“使用 meeting-notes 整理以上会议，仅输出待办事项。”

预期：只出现“检查搜索页面”等待办，负责人为丙；不要写成“周五已经决定上线”。截止时间如未明确确认，写待确认。

**请求 B**：“使用 meeting-notes 总结哪些发布决定已经确认。”

预期：不把“建议周五上线”当成已经达成一致的发布决定。可以说明该发布时间尚未确认。

### 记录实际结果

| 检查 | 预期 | 实际结果 | 证据 |
| --- | --- | --- | --- |
| 结构检查 | `SKILL.md` 元数据有效 | 待填写 | 验证器输出 |
| 环境发现 | 客户端识别到该 Skill | 待填写 | 技能列表或界面 |
| 显式调用 | 执行 meeting-notes | 待填写 | 执行轨迹 |
| 输出边界 | 请求 A 只输出待办 | 待填写 | 实际输出 |
| 事实判断 | 请求 B 不伪造发布决定 | 待填写 | 实际输出 |

如果客户端没有提供可靠的“所选技能”观测方式，不能仅凭答案像会议纪要就认定它真的调用了该 Skill。

## 六、工程思想：复用不是把所有要求写死

真正值得复用的是**方法**，不是**每次的结果**。

- **抽象**：从不同会议中找出稳定的判断规则。
- **封装（Encapsulation）**：把规则与可选资源放进一个有明确用途的技能目录。
- **参数化**：保留本次会议材料、输出范围等变化内容，由用户请求提供。
- **单一职责**：不要让 meeting-notes 顺手承担与会议整理无关的审批权。

这里与普通函数的设计有相似之处，但不能简单等同：函数具有由程序控制的执行语义，Skill 则通过模型理解自然语言约束，其行为并不总是确定性的。

## 七、总结与下一步

现在我们从重复请求中提炼了一个最小 `SKILL.md`，并且知道如何区分“文件能解析”“客户端能发现”“结果符合要求”。

**本篇最重要的结论**：Skill 的价值不在于文件越多越好，而在于任务边界清楚、稳定规则可复用，且能够用实际请求检验效果。

但还有一个问题：即使文件内容完全正确，**用户没有点名 Skill 时，Agent 为什么有时不会自动使用它？**
