# 让程序结构可理解

> **阅读索引**：工程故事路线第 3 篇。前置：[从代码到机器动作](../02-Computer-Architecture-and-Organization/from-code-to-machine.md)。下一篇：[正确之外，还要考虑规模](../04-Data-Structures-and-Algorithms/algorithm-performance-tradeoffs.md)。

## 故事：批量重命名误伤了注释

团队用字符串替换来改函数名，结果注释和局部变量也被误改，部分文件还出现语法错误。脚本只看见字符，没有理解字符在程序里的角色。

## 为什么要理解它

编程语言定义怎样表达计算，以及哪些程序形式合法、含义是什么。编译器或解释器需要从字符识别结构，才能检查、转换或执行；编辑器的跳转、补全和安全重构也依赖类似结构信息。

## 核心原理

词法分析把字符分成标识符、数字和运算符等记号；语法分析根据语言规则组织这些记号，常见表示是抽象语法树（Abstract Syntax Tree, AST）。例如表达式 1 + 2 * 3 的树形结构体现乘法先于加法。

类型检查验证操作是否符合类型规则；之后实现可能生成中间表示、机器码，或交由运行时执行。不同语言流程有差异，不是每种语言都以完全相同的步骤实现。

## 工程上解决什么

结构化表示比纯文本搜索更适合程序分析与转换。重构工具可以修改函数调用位置而不改动注释中的同名字串；静态检查器可以发现某类类型错误。语法正确仍不代表业务逻辑正确。

## 常见误区

- AST 描述语法结构，不包含全部运行含义。
- 静态类型系统只能检查它表达的属性。
- 代码能解析，不代表代码满足用户需求。

## 工程哲学：在正确的抽象层修改问题

处理程序结构时使用结构化工具；检查运行结果时执行程序或测试。选择能表达目标约束的表示方式，比在错误的抽象层反复打补丁更可靠。
