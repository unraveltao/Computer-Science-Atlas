# Git 与 GitHub 协作工作流

> **阅读索引**：Tools 实践文章。前置知识：[安全地推进软件改动](../Computer-Science/08-Software-Engineering/engineering-change-safely.md)。下一篇：[用 Codex 完成可审查的开发任务](./codex-assisted-development.md)。

## 故事：两个人同时修一个问题

小林修复订单折扣，小周调整订单页面。两人都要修改同一个项目。如果只靠发文件，谁的版本更新、哪些内容被覆盖、什么时候整合都会难以追踪。

Git 和 GitHub 把协作过程拆成可见的小步。Git 在本地记录项目快照；GitHub 托管远端仓库并提供讨论、评审和合并界面。Git 不依赖 GitHub 才能运行，GitHub 也不能替团队判断改动是否正确。

## 为什么要理解它

版本控制减少成果丢失、无关改动混杂和盲目合并的风险，也让团队能回答“谁改了什么、为什么改、如何验证”。

## 核心原理

提交（commit）记录一次项目状态及其元数据。分支（branch）是指向提交历史的引用，让多项工作可以独立推进。远端（remote）是本地仓库记录的另一个仓库地址。推送（push）发送本地提交，拉取（pull）获取并整合远端变化。

Pull Request（PR）是 GitHub 上提出和讨论一组改动的协作请求。它不是 Git 的核心对象，而是把分支差异、评审、自动检查和合并组织在一起。

## 一次安全的协作流程

~~~bash
git status
git switch -c fix/order-discount
# 编辑并检查改动
git diff
git add path/to/changed-file
git commit -m "fix: handle overlapping discounts"
git push -u origin fix/order-discount
~~~

之后在 GitHub 上创建 PR，说明问题、方案和验证方式。查看文件差异，回应评审意见，再按仓库规则合并。提交前检查状态和差异，避免把无关改动一起带入。

## 常见误区

- commit 保存在本地，push 才发送到远端。
- 分支通常是历史引用，不是额外复制一整套文件夹。
- PR 提供讨论和检查入口，但不自动保证功能正确。
- 自动检查通过不代表满足所有业务需求；还需要评审和适当的行为验证。

## 工程哲学：让改动可见、可讨论、可回退

小而聚焦的提交更容易审查；但过度切分也会增加整合成本。目标是让每组改动足够独立，使读者能说明它为何存在、如何验证。

## 工具思维实验室（Tool Thinking Lab）

下面的问题没有唯一正确答案。请先写出你的约束和判断依据，再对照参考答案要点。

### 情境一：远端平台暂时不可用或停止维护

团队的 GitHub 仓库正在进行发布。平台通知部分功能可能中断，团队需要决定是否迁移。

**思考题**

1. 哪些能力必须保留？哪些工作可以先依靠 Git 本地仓库继续？
2. 比较“暂缓外部协作并等待恢复”和“迁移或临时镜像到另一个托管平台”两种方案。迁移前后需要盘点和验证什么？
3. 什么变化会让你从暂缓转向迁移？

**参考答案要点**

- 先区分 Git 保存的提交历史，与托管平台上的 Issue、PR 讨论、权限、自动化和发布等协作数据。只迁移代码远端不一定迁走所有协作上下文。
- 方案 A：保留本地仓库与现有远端，短期暂停依赖平台的工作。优点是迁移成本和数据风险低；代价是协作或发布能力受限。适合中断短、工作可等待、已有本地备份的情况。
- 方案 B：建立临时镜像或迁移到另一托管平台。优点是恢复协作；代价是权限、CI、密钥、Issue/PR 等数据可能需要重新配置，双远端也会产生分叉风险。应避免无规则的双写。
- 盘点提交、分支、标签、LFS 对象、发布产物、Issue/PR 记录、自动化配置、权限和凭据。验证镜像的提交与引用、克隆和推送、必要工作流、权限以及回退办法。
- 推荐先评估中断时长和业务容忍度，准备可恢复备份；只有确认是长期或不可逆变化时才做完整迁移。若出现合规要求、平台终止服务或恢复时间超出业务容忍窗口，结论可能改变。

### 情境二：一体化平台还是专用工具组合？

独立开发者要管理需求、改代码、测试、部署网站和维护文档。一体化平台覆盖约 80% 的需求；组合 GitHub、Codex、Vercel 和文档工具能覆盖更多场景，却增加配置和维护。

**思考题**

1. 给每个工具划分什么职责？哪个系统应作为需求、代码和发布状态的事实来源？
2. 比较一体化方案与专用工具组合的短期收益和长期成本。用哪些约束做决定？
3. 如果某个集成中断，你希望数据流如何降级或恢复？

**参考答案要点**

- 先绘制工作流：需求记录 → 代码变更 → 自动检查 → PR 评审 → 预览部署 → 发布说明。明确每一步的数据所有者、写入方、只读方和失败处理。
- 方案 A：一体化平台。集成较少、初始维护较轻；但可能缺少必要能力、降低替换灵活性，或把多个重要数据放在同一平台。适合需求较简单、维护时间有限、平台覆盖面足够的情况。
- 方案 B：专用工具组合。可以按任务选择更合适的能力；代价是 API、权限、重复数据、通知和故障恢复的集成负担。适合特定能力明显重要，且团队有资源维护连接的情况。
- 不要只比较功能百分比。还应评估任务频率、失败影响、数据可迁移性、权限边界、成本和替换难度。尽量为 Issue、代码和发布各指定唯一事实来源，避免人工同步多个副本。
- 推荐先用最少工具闭环完成一次真实发布，再根据缺口增加工具。若集成维护成本超过节省的时间、数据不可导出或团队规模显著增长，应重新评估架构。

### 情境三：每天手动复制 Issue 状态值得自动化吗？

开发者每天把 GitHub Issue 的状态复制到另一份项目文档，偶尔漏改或覆盖了较新的状态。

**思考题**

1. 如何确认这是值得解决的重复劳动，而不是偶发操作？
2. 比较保留人工更新、使用现成集成、调用 API/Webhook 或编写定时脚本。
3. 自动化后如何处理重复事件、权限不足、失败重试和状态漂移？

**参考答案要点**

- 先测量频率、每次耗时、错误代价和真实使用者；确认两个地方都需要维护该状态。
- 方案 A：保留人工更新，并使用文档链接回 Issue。最简单、易观察；如果任务很少，自动化的建设和维护成本可能更高。
- 方案 B：使用现成集成或事件驱动自动同步。响应及时，但要确认字段映射、权限和集成可用性；失败时要能发现和恢复。
- 方案 C：用 API 或脚本定时拉取。实现可控，但有凭据轮换、速率限制、重试、日志和脚本维护成本。
- 先指定唯一事实来源，并设计幂等写入、可观测失败和人工校正路径。用重复事件、无权限和目标服务不可用做小规模验证。
- 用节省的时间和减少的错误与开发、运行、排错和维护时间比较。若频率或错误代价很低，维持手动流程可能更合算；若同步影响交付或合规，自动化优先级会上升。
