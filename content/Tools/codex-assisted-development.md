# 用 Codex 完成可审查的开发任务

> **阅读索引**：Tools 实践文章。前置：[Git 与 GitHub 协作工作流](./git-and-github-collaboration.md)。延伸学习：[智能体技能工程](../Computer-Science/11-AI-and-Agent-Engineering/agent/skill-engineering/index.md)。

## 故事：修复一个“偶尔丢失”的设置

用户报告：“我关闭提醒后，重启应用，它又打开了。”如果只说“修好设置”，工具必须猜行为、代码位置和验收标准。代码可能看起来合理，实际仍没解决用户的问题。

## 为什么要理解这项工具

Codex 可以协助阅读代码、提出计划、修改文件和运行检查，但它不会自动知道没有提供的产品背景，也不能仅凭解释证明行为正确。使用者需要把问题说清楚，并负责审查结果。

## 一次可审查的任务

可以这样描述：

> 目标：修复关闭提醒后重启又开启的问题。  
> 现象：设置页显示已关闭，但重新启动后读到旧值。  
> 约束：保持现有设置格式和公开接口，不改动其他偏好项。  
> 验收：更新设置后重新载入仍为关闭；旧设置缺少该字段时保持兼容。请先检查相关数据流，再给出计划；完成后说明改动文件、验证命令和未覆盖风险。

随后完成开发闭环：检查它定位的读写路径和根因；确认计划符合范围；审查完整差异；运行相关检查并阅读结果；对不确定行为补充测试或缩小结论；最后通过 Git 提交和 PR 记录改动。

## 常见误区

- 提示越详细不等于输出必然正确；它只减少歧义。
- 最终总结是说明，不是证据；要看实际差异和命令结果。
- 不要默认工具已经理解仓库规则；确认项目指引和测试约定适用。
- 若发现必须扩大重构范围，应先重新拆解任务。
- 一次测试成功只证明该测试在该环境中的断言通过。

## 工程哲学：把判断留给人，把重复劳动交给工具

搜索、生成候选方案和执行清楚定义的检查适合自动化；目标排序、风险接受和发布决定仍需依据上下文判断。好的人机协作让结果更容易检查，而不是让检查变得多余。

## 工具思维实验室（Tool Thinking Lab）

这些情境用于练习工具选择、组合、迁移和工作流设计。请说明约束与验证办法；参考答案展示多种可行判断，不指定唯一产品。

### 情境一：这个任务是否应该交给 Codex？

你要处理三项工作：格式化几百个文件、调查一个跨模块缺陷、改写一个尚未明确验收标准的支付流程。

**思考题**

1. 哪项适合交给确定性脚本或格式化工具，哪项适合 Codex 辅助，哪项应先补充需求？
2. 比较“人工处理”“脚本/现有工具”“Codex 协助”三种方式的风险、效率和验证成本。
3. 你的选择会如何随任务影响范围、数据敏感度和可测试性改变？

**参考答案要点**

- 格式化通常适合确定性格式化器：结果可重复，成本低；人工或模型逐文件改动难以保证一致。
- 跨模块缺陷可由 Codex 帮助检索调用关系、提出修复候选，但应先提供复现、相关代码和验收标准，检查差异并运行针对性测试。它适合减少搜索与重复编辑，不替代故障证据。
- 支付流程需求不清时，优先澄清业务不变量和失败语义。直接让模型“重写”会放大猜测风险；先建立规格和测试，再选择实现工具。
- 决策时比较任务重复性、规则确定程度、上下文是否可提供、错误影响、隐私要求和结果可验证性。支付任务的风险更高、验收不清时，应先停止实现；如果只是低风险、可回退的局部改动，Codex 可以更早参与。

### 情境二：Codex 暂时不可用或不再合适，怎样迁移？

团队依赖 Codex 做日常代码修改；现在价格或可用性发生变化，团队想保留稳定的开发能力。

**思考题**

1. 哪些工作方法和项目上下文应与具体产品解耦并继续保留？
2. 比较“暂停 AI 辅助并继续人工工作”和“试用另一个编码 Agent”两种方案。迁移前应保留或重建什么？
3. 怎样验证替代方案达到团队需要，而不是只凭一次演示？

**参考答案要点**

- 将长期有效的需求、架构边界、AGENTS.md、构建命令、测试、代码规范和评审流程保存在仓库或团队控制的文档里。把会话历史、产品专用界面步骤和临时提示视为可迁移性较弱的上下文，不要把它们当作唯一知识库。
- 方案 A：暂停 AI 辅助，继续人工完成高优先级任务。优点是无需迁移和重新授权；代价是吞吐量或开发体验可能变化。适合任务量低、替代工具风险尚未评估的阶段。
- 方案 B：试用另一个编码 Agent 或 IDE 工具。优点是恢复部分辅助能力；代价是输出质量、权限模型、上下文处理、集成方式和成本都可能不同，需重新评估。
- 用一组真实、可回滚的代表任务做试点，记录任务完成质量、人工审查时间、验证结果、失败模式和总成本；同时验证隐私/权限边界、可取消操作和仓库工作流。
- 推荐先保证人工可继续交付，再做小范围试点，不要在关键发布前一次性迁移。若任务高度依赖某种专有能力、数据合规禁止外部工具，或替代工具无法可靠执行验证，结论需要调整。

### 情境三：如何组合 Issue、Codex、GitHub 和部署预览？

一个功能需求需要从任务拆分走到上线。团队可用 Issue 管理目标，让 Codex 辅助实现，用 GitHub PR 评审，并通过部署预览检查用户界面。

**思考题**

1. 为每个工具分配什么职责？哪个记录是需求、代码和验证结果的事实来源？
2. 设计数据流和人工检查点；如果 Agent 修改错误文件、测试失败或预览不可用，流程如何停住和恢复？
3. 哪些步骤值得自动化，哪些决定应保留给开发者或维护者？

**参考答案要点**

- 一种可行组合是：Issue 保存目标与验收；Codex 在隔离的工作分支修改代码；Git 保存差异；GitHub PR 保存审查与检查结果；预览部署用于观察构建后的页面。每个系统只负责适合它的记录，不必同步整份内容。
- 方案 A：人工逐步操作。透明、容易临时调整；代价是重复步骤和遗漏风险。适合低频或流程尚未稳定时。
- 方案 B：自动化格式检查、测试、预览生成和状态链接。重复工作较少；代价是集成权限、失败通知、重试和维护成本。适合流程稳定且验证规则明确时。
- 让 Agent 只在授权范围内修改；开发者检查差异和测试结果；PR 评审决定代码是否可合并；发布仍遵守项目权限。测试失败或预览不可用时，明确阻断对应验收，不把“部署作业已结束”当成“功能已验证”。
- 推荐先稳定人工工作流，再把重复、可观察、可回退的步骤自动化。若自动化故障会造成错误发布或泄露数据，增加人工关卡或缩小权限。
