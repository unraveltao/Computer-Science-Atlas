# 知识领域与归档边界

本文记录 Atlas 已批准的 14 个一级知识领域、内容归属原则，以及与 Exploration、Tools 和项目知识库之间的链接规则。它是内容分类决策的维护文档；领域首页用于读者导航，具体概念文章则解释主题本身。

## 归档原则

1. 保留现有 14 个一级领域的名称、顺序和主要归属。新增、重命名或移动一级领域前，先提出明确提案并获得维护者批准。
2. 每篇知识文章只有一个主要归属。按文章主要回答的问题和分析层级选择领域；在文章中说明相邻范围，并链接到相关页面。
3. 跨领域主题通过链接表达关系，避免在多个领域维护同一份定义、原理或教程。必要时可以在另一个领域解释该概念在本领域中的具体应用，但要链接到唯一的规范页面。
4. 领域首页的主题清单是范围与建设计划，不代表相应主题已有完整文章。
5. 为已经公开的页面选择归属时，优先维持稳定路径；若确需迁移，应在提案中列明旧链接兼容和重定向计划。

## 跨知识分支的规范归属

| 内容类型                                                           | 规范归属                     | Atlas 中如何连接                                                               |
| ------------------------------------------------------------------ | ---------------------------- | ------------------------------------------------------------------------------ |
| 通用思维与跨领域方法，例如第一性原理、系统思维、反馈回路、决策理论 | 独立的 Exploration 知识分支  | Atlas 通过链接到规范内容；只解释该方法在具体计算机领域中的应用，不复制通用理论 |
| GitHub、Codex 等工具的操作和使用流程                               | Tools 知识分支               | Atlas 保留版本控制、Agent 工程等技术原理，并链接到工具使用指南                 |
| 某个项目的设计选择、实验过程与实施记录                             | 对应项目的 Project Knowledge | 从 Atlas 链接相关基础概念；项目记录不替代规范知识文章                          |
| 可复用于多个学科的机制或原理                                       | 其最主要学科领域             | 其他领域在需要时引用同一个规范页面，并解释本领域的应用                         |

“规范归属”表示该内容的唯一主要维护位置。链接到其他知识分支不代表自动同步；维护者应在相关变更中检查指向是否仍然有效。

## 跨领域链接写法

- 先确定文章回答的核心问题，再选择一个主要领域；不要因为文章引用了多个学科就复制到多个目录。
- 链接文字应说明目标概念或领域，并保持中文可见文字；目标路径使用稳定的英文文件路径。
- 在交界处用一句话说明两篇内容的分工，例如“本文讨论协议传输；跨服务状态和故障处理见分布式系统”。
- 不要仅为满足链接数量而添加无语义关系的链接。相关链接应解释“为什么相关”或“区别在哪里”。
- 若现有范围无法容纳一类持续出现的新主题，先提交范围提案，列出示例、相邻领域和迁移影响；不要直接新建一级领域或批量迁移内容。

## 本轮审计结论

本轮逐一查看了 14 个领域首页的代表性主题、领域边界和相关领域链接。现有首页已经覆盖各自学科的主要边界，且通过链接连接了多个相邻领域；未发现需要调整一级领域或移动现有内容的证据。需要持续留意的交界包括 08/09（软件工程与系统架构）、05/13（操作系统与基础设施运维）、06/09（网络协议与分布式语义）、07/09（数据库内部与跨节点一致性）、08/12（工程过程与应用产品）以及 11 与通用软件架构的关系。

此前提出的主题扩展建议仅是后续规划候选，不代表批准新增文章。新增文章应使用独立 Issue 明确问题、唯一归属、与既有页面的差异和验收依据，再逐项实现。
